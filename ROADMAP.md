# Дорожная карта PriceAggregator

## Заметки по репозиторию
- `tests/fixtures/` **в git не игнорируется** и это осознанно: фикстуры —
  слепки живых ответов сетей, без них юнит-тесты нечего проверять, а
  домен прямо требует «сломанная вёрстка роняет тест, а не молчит».
  Держат их компактными (обрезанный payload, а не вся страница), чтобы
  репозиторий не раздувался.

## Фаза 0 — Фундамент (готово)
- Скелет Electron + React + SQLite, сборка setup + portable, автообновления из Releases.
- **Починено в 1.2.0: БД не открывалась ни в dev, ни в собранном exe.**
  `db.ts` читал `schema.sql` с диска рядом с бандлом, а `tsc` не копирует
  `.sql` и `build.files` перечисляет только `dist/` и `dist-electron/` — схемы
  там не было. Падение глотал `catch` в четырёх вызовах `openDb`, приложение
  жило с `database = null`; а синглтон присваивал объект до `exec(schema)`,
  поэтому после первой ошибки все последующие вызовы получали базу без таблиц
  («no such table: products»). Итог: write-on-change, история и «Не
  разложено» молча не работали. Теперь схема — генерируемый `src/core/db/
  schema.ts` (`npm run gen:schema`, вызывается перед сборкой), `openDb`
  откатывает базу при провале схемы, `persistDb` бросает ошибку при провале
  записи, а `test:db` роняется, если схема разошлась с `schema.sql`. Проверено
  на скомпилированном `dist-electron`: 5 городов и 9 магазинов засеяны,
  `savePriceIfChanged` пишет, файл БД появляется на диске.
- Адаптер Магнита (Москва/Ульяновск/СПб): search + fetchProduct + категории.
  **Категории починены 2026-10-08:** витрина больше не лежит в __NUXT_DATA__
  (в живом ответе 0 вхождений "g123" и 0 вхождений /catalog/ — вместо них
плоский Nuxt-массив devalue со ссылками на индексы, где у категории есть
  `id`/`name`/`code`/`image`/`children`, но нет URL). Плитки пришли обычными
  `<a>` в HTML главной: класс `catalog-categories-tiles__item`,
  `href="…/catalog/<id>"`, название в `alt` картинки, картинка в `src`,
  а подпись — в `<span class="…catalog-categories-tiles__text">` внутри
  `<!--[-->…<!--]-->`. Разбираются **8 верхнеуровневых плиток** (не 40:
  столько плиток витрины у сети), товары по ним берутся прежним путём через
  JSON-LD. Разбор ищет плитку по открывающему `<a>` (порядок атрибутов
  меняется), тело берёт до следующего открывающего `<a` (незакрытая плитка не
  съедает следующую) и снимает SSR-комментарии перед разбором подписи.
- Адаптер Пятёрочки: нормализация по живым ответам (выдача + карточка +
  товар вне наличия), тест `npm run test:5ka`. Браузерный транспорт
  (Playwright Firefox) рабочий и включён: `ready:true` для `35XY`, Firefox едет
  в сборку (`resources/browsers`), магазин подобран — см. Фазу 1.
- Города: Москва / Ульяновск / Санкт-Петербург, переключение dropdown'ом.
- Матчер товаров (название + бренд + фасовка; штрих-кодов нет ни у 5ka,
  ни у Магнита), карточка с ценами по магазинам без дублей.
- БД в проде (`sql.js`, без нативных модулей): savePriceIfChanged пишет
  историю; скидка — три состояния (не знаю / нет / есть).
- Планировщик опроса (6ч, fetchProduct, паузы, статус) + график истории.
- Аудит зависимостей: `npm audit` — 0 уязвимостей, `pip-audit` — 0
  (обновлены `pip` и `setuptools` внутри `.venv`).

## Заметки по данным
- Смена кода магазина в городе = смена цен: ключ истории
  (canonicalId, storeId, city, storeCode) код точки содержит, поэтому старая
  точка и новая — это РАЗНЫЕ линии графика, и удалять записи вручную не нужно
  (раньше ключ кода не содержал, и старые записи склеивались с новыми, а
  первый опрос записывал ложное «изменение цены»).
- Локальные ключи браузера: у Пятёрочки кука `5ka_store_id_store` и
  `DeliveryPanelStore.selectedStore.sapCode` — это **код магазина** (одно и
  то же значение), а не города. У Ленты наоборот: `App_Cache_City` /
  `App_Cache_CitySlug` — про **город** (`slug: ulyanovsk`, `id: 107`),
  storeId надо смотреть отдельно при выборе магазина. И заголовок
  `X-Domain` у Ленты — это slug **региона** из `region/list`, а не наш id
  города: СПб = `spb`, Краснодар = `ksdr`, Ульяновск = `ulyanovsk`
  (в `lenta.ts` отдельная карта, подставить свой id нельзя).
- HAR/capture сети лежат вне репозитория (внутри живые `PassportAccessToken`
  и `PassportRefreshToken` юзера, `qrator_*`, `Utk_*`); `*.har` и
  `lenta-probe/` в `.gitignore`. В фикстуры попадает только форма ответа.
- Закрыто: `product_links` переведён на PRIMARY KEY
  `(canonical_id, store_id, city, store_code)`, оба чтения джойнят с городом
  (миграция `migrateStoreCodes`, `db.ts:353`). Раньше город в ключе не было,
  и `store_sku`/`url`/`image_url` перезатирались между городами.
- Инвариант для каждой новой сети: **HTTP 200 не значит «наш магазин»**.
  У Магнита неизвестный shopCode молча подменяется дефолтным
  (`assertOwnStore`, `magnit.ts:54`). У Ленты привязка магазина идёт через
  сессию, поэтому сверка двухслойная: ответ `delivery/mode/set` должен
  вернуть наш `storeId`, а в теле карточки `storeId` — это **alias**
  (`"3090"`), а не id точки (`4161`); две независимые нумерации, в
  `stores/pickup/search` (1020 точек) `id === Number(alias)` не совпало ни
  разу. В выдаче поиска `storeId` нет вообще — сверять там нечем, поэтому
  слой первый обязателен.

### Светофор `svetoforonline.ru` — каталог в статическом JSON

- [x] **Адаптер.** Прайс магазина — один статический JSON, поэтому
      **кэшируется по ключу `(домен, shopid, offersupd)`** (TTL 30 мин, старые
      ключи домена вытесняются) и обслуживает оба метода: `search` фильтрует
      список локально (кап 40), `fetchProduct` достаёт `id` из того же файла.
      Без кэша опрос 76 товаров скачал бы ~19 МБ и 76 файлов — домен
      заблокирует.
- [x] **Файл прайса — массив**, а не объект-карта (`[{"id":104255,…}]`).
      Первая версия фикстуры была пересобрана руками в объект, и это скрыло
      главный баг: адаптер, отвергавший массив, не отдал бы ни одной цены.
      Фикстура теперь снята как есть, и тест падает, если её формат переделать.
- [x] **Домен берётся у магазина, а не у города.** Москва разложена по доменам
      `moskovskaya-oblast`, `moskva-vostok`, `moskva-yug`, `moskva-zapad` и
      другим, метка выгрузки у каждого своя. Справочник хранит пару
      `shopid -> домен` (636 точек, 40 регионов), `svetofor:regions` его
      пересобирает. `shopid` при этом берётся **только из конфига**: на странице
      домена лежит точка по умолчанию (в `moskovskaya-oblast` это 838, а не
      наш магазин).
- [x] **Метка прайса — региональная, а не магазинная** (проверено: у трёх
      разных магазинов одного домена файлы разные — 553 / 576 / 545 товара — а
      метка со страницы одна). Метка читается со страницы домена, кэшируется на
      час, а 404 на файле означает протухшую метку: метка сбрасывается, домен
      перечитывается один раз, файл запрашивается повторно, и только потом
      бросается отказ сети.
- [x] **`c` — себестоимость, а не старая цена** (проверено на 552 товарах
      одного магазина: `0 < c < p` у подавляющего большинства, `c > p` у
      единиц — данные с ошибкой, `c = 0` тоже бывает). Значит `promoPrice` и
      `oldPrice` у Светофора — всегда `null`, как у Магнита, а `c` в базу не
      пишется вообще. Иначе в историю уехала бы закупочная цена.
- [x] **`p` — цена в копейках** (проверено на живых ответах: `p=11850` →
      118,50 ₽, `p=12738` → 127,38 ₽ — копейки не круглые).
- [x] **Свежесть прайса — по файлу, через максимум `d`** (unixtime). Важная
      поправка: `d` — это ПОСТРОЧНАЯ отметка позиции, а не дата выгрузки: в
      живом прайсе 552 строк несут 37 разных `d` с размахом в 22 дня, и 7 из них
      старше недели — это обычные позиции. Резать по построчной метке нельзя:
      такой SKU навсегда исчез бы из поиска и из карточки (цена перестала бы
      обновляться, счётчик ошибок рос бы на каждом опросе). Заброшенные точки
      видно по максимуму — у магазина 376 весь файл от 2021 года — и тогда бросается
      **`StaleStoreError`**, новый третий класс рядом с `ProductLookupError`. Он
      означает «сеть жива, но этот магазин она не обновляет», поэтому такой отказ
      не должен ни растить `strikes`, ни ставить сети паузу: две протухшие позиции
      подряд (а позиции одного магазина в `prices_history` идут подряд — нет
      `ORDER BY`) иначе погасили бы сеть вместе с живым магазином другого города.
      Отчёт опроса получил поле `staleStores`, чтобы такие точки были видны
      отдельно от сбоев сети. Тот же класс — на файл без дат позиций: это дрейф
      формата, и молчать о нём нельзя. Из-за этого заведены живые точки: Москва 820
      (Жулебино), СПб 206 (Александровской Фермы); 376 и 682 не берём. Порог —
      14 дней: у живой точки 820 самая «долгая» позиция старше недели на сутки, а у
      по-настоящему заброшенной протух весь файл. Отказ кэшируется, иначе один
      обход 40 позиций скачал бы протухший файл 40 раз (10 МБ и таймаут на каждой).
- [x] **`articul` — не штрихкод:** артикул из 7 цифр, EAN-13 не найден ни у одного
      товара из 552. В `barcode` его класть нельзя: расхождение barcode жёстко
      запрещает склейку, и появление любой сети с настоящим EAN убило бы склейку
      со Светофором молча. Решено: в склейку не идёт.
- [x] **Фасовка — из названия, а не из `w` и не из `ei`.** `ei` = «шт.» или
      «кг.» (где «кг.» значит «продаётся на вес»), а `w` — объём/вес упаковки в
      граммах без единицы: и «Молоко 1 л», и «Арахис 1 кг» — это `w = 1000,
      ei = 'шт.'`, а у «Сухари 500 гр» в названии `w = 1000`. Фасовка разбирается
      из названия (448 строк из 553), с переводом «3000 гр → 3 кг» и «5000 мл →
      5 л».
- [x] **`id` — SKU сети, а цены per-store.** В пределах домена `id` общий у
      точек (из 553 товаров 820 у 488 тот же `id`, что у 377, у 447 из них та же
      цена), а между регионами пересечение крошечное (12 из ~550) — assortment

- [x] **Наличие:** отдельного флага нет, значит правило как у Ленты: товар есть в

## Фаза 6 — Несколько точек на город (шаги 1–8 сделаны, приняты ревью)

Задача: чтобы в одном городе можно было следить за несколькими точками одной
сети (две точки Магнита в СПб) и сравнивать цены между ними.

**Сделано:**
1. **Шаг 1 — контракты адаптеров.** `PricePoint.storeCode` обязателен, девять
   мест сборки товара его проставляют, кэш полки хранит sentinel `'?'`, IPC
   перенесён на шаг 4. Гейт зелёный, живой Магнит вернул `storeCode: 303857`.
2. **Шаг 2 — атомарная миграция БД и переключение ключа.** Ключ везде
   `(canonical_id, store_id, city, store_code)`; копия `.pre-phase6.bak` до
   первой перестройки; пересборка таблиц с откатом и проверкой FK; перенесённые
   строки помечены `'?'` и не заводят вторую сущность (избранное, полки,
   ссылки). Гейт 100/100/100/100, на копии реальной базы 723 цены, 865 полок,
   583 ссылки, нарушений FK 0, дублей нет.
3. **Шаг 3 — каталог точек.** В `catalog.ts` появились `storesForCity`,
   `readyStoresForCity`, `storeByCode`, `storeIdsForCity`, `networksForCity` и
   `uniqueByNetwork`; все самописные `find(s => s.storeId === …)` в `src/`,
   `electron/` и тестах заменены на них. Код точки уникален внутри (сеть, город)
   и у точек одной сети разные имена — это проверяет `npm run test:db`. Записан
   явный путь добавления точки. Гейт 100/100/100/100.
4. **Шаг 4 — ядро.** Заглушка «первая точка сети» удалена: код точки приходит
   от того, кто показывает товар, и обязателен в скоупах, истории, избранном и
   блоке цен. Правило перенесённой отметки (`'?'`) общее для базы и интерфейса,
   ключи состояния renderer поточечные, между двумя запросами в одну сеть стоит
   пауза, счётчики считают сети, уведомление называет точку. Гейт 100/100/100/100.

**Дальше:** шаги 5–8 закрыты (подтверждение кода сетью, склейка, поточечный
   опрос и чек-лист, поточечный UI с галочками, адресом из сети и агрегатом
   «от … до …»). Оставшийся намеренно не закрытый долг — в
   `.agent/tasks/phase6-multi-store/spec.md`: адреса точек, которых нет в сети,
   и формат точки Магнита (`x_shop_type`) для реального второго магазина.

**Почему нельзя просто добавить строку.** `stores` имеет PRIMARY KEY
`(id, city)` — одна сеть, одна точка на город. Ключ цены
`(canonical_id, store_id, city)` кода точки не содержит, поэтому две точки
одной сети делили бы цену и историю. Ровно это уже произошло при смене кода СПб
(`501478` → `277027`). Значит точка обязана стать частью идентичности цены.

**Что уже известно из разбора (блокеры):**
1. **Сид `stores` убьёт базу.** После смены PK на `(id, city,
   external_store_id)` оператор `ON CONFLICT(id, city) DO UPDATE` перестанет
   быть валидным — SQLite отвергнет весь `exec(SCHEMA)`, и `openDb` начнёт
   отдавать `database: null` (цены на экране есть, история мертва). Сид надо
   переписать так, чтобы он и вставлял новые точки, и обновлял существующие.
2. **`stores` не источник правды.** Её не читает никто, кроме сида и двух
   тестов; список точек для UI, опроса и витрины — `CITY_STORES` в
   `catalog.ts`. Значит `CityStoreInfo` должен уметь держать несколько
   записей на `(storeId, city)`, а все `find(s => s.storeId === …)` — искать
   ещё и по коду. Нужен явный путь добавления точки.
3. **Планировщик возьмёт не ту точку.** `scheduler.ts` ищет точку по
   `storeId` и возьмёт первую: товар, отслеживаемый по точке Б, будет опрошен
   по коду точки А и записан в ключ точки Б. Код точки должен входить и в цель
   опроса, и в резолв контекста (`services.ts`, `App.tsx`).
4. **Код точки должен приходить от сети, а не из конфига.** Сейчас
   `storeItems` намеренно перебивает `storeId`/`city` ответа на
   опрашиваемую сеть — и это правильно. Новая колонка фиксировала бы, что мы
   ПОПРОСИЛИ, а не что сеть ОТДАЛА, а это главный инвариант («успешный HTTP ≠
   наш магазин»). Значит `ScrapedProduct`/`PricePoint` несут подтверждённый
   код, и расхождение с настроенной точкой — громкая ошибка без записи.
5. **Сессия Ленты кэшируется по городу.** Две точки будут драться за одну
   сессию (`sessions`/`inflight` по ключу `city`, привязка — мутабельное
   поле). Ключи должны стать `city:storeId`.
6. **`groupByProduct` глушит вторую точку.** Дедуп по `storeId + canonicalId`,
   а `canonicalId` сетевой, то есть у двух точек он ОДИНАКОВ: второй offer
   молча уходит в `continue`, и сравнение между точками физически не
   отобразится. Слой склейки в плане обязателен.
7. **Миграция `favorites` станет бесконечной.** Предикат `keyOk` проверяет
   длину PK (3) — с новой колонкой он всегда false, и таблица будет
   пересобираться при каждом запуске. То же для `product_categories` и
   `product_category_manual`: PK через ALTER не меняется, нужна пересборка с
   recreate индексов и сохранением FK.
8. **Индекс `idx_prices_lookup` сам не обновится.** `CREATE INDEX IF NOT
   EXISTS` оставит старое определение — нужен явный `DROP INDEX IF EXISTS` в
   миграции (ровно механизм, из-за которого в проекте появились миграции по
   форме таблицы).

**Миграция данных (пересмотрена).** Молча заливать код из `catalog.ts` по паре
`(store_id, city)` нельзя: в старых строках кода нет, и заливка склеит две
разные точки СПб обратно — тот самый дефект, ради которого фаза и затевается.
Правильное правило: **новая точка = новая история**.
- Строки без кода получают sentinel (например, `?`) и подписываются на
   графике как «точка не указана», а не как текущая.
- write-on-change никогда не сравнивает точку `?` с реальной: первая запись
  по новой точке — это новая линия, а не «изменение цены».
- Смена кода в `catalog.ts` больше не склеивает кривые: старые строки остаются
  со своим кодом.

**Что меняется по слоям:**
- **Схема:** PK `stores` → `(id, city, external_store_id)` + `address` (колонка
  уже есть и не используется); `store_code` в `prices_history`, `favorites`,
  `product_categories`, `product_category_manual`; миграция по форме с
  пересборкой таблиц и индексов; старый `exe` на мигрированной базе читать её
  нельзя — предупреждение пользователю плюс порядок бэкапа файла.
- **Не трогаем:** `products`, `cities`, `product_splits` — точек не содержат.
- **Контракты:** `storeCode` — обязательное поле (проект компилируется с
  `exactOptionalPropertyTypes`, опциональное поле позволит renderer'у его не
  передать, и ключ молча станет пустым).
- **Адаптеры:** подтверждённый сетью код в `ScrapedProduct`; у Магнита он уже
  есть в сверке, у Пятёрки приезжает из URL каталога, у Ленты — из
  `mode/set` и alias.
- **Ядро:** `savePriceIfChanged`, `latestPrices`, `getPriceHistory`,
  `listTrackedProducts`, `checkTargets`, `saveNotifiedPrices`, полки,
  `getHistory` и preload.
- **Склейка:** `matching.ts` перестаёт дедуплицировать по `storeId` и
  различает точки.
- **Опрос:** цель — `(canonical, store, city, code)`; точки одной сети идут с
  паузой `SAME_STORE_POINT_PAUSE_MS` между запросами (иначе два запроса уйдут в
  один домен подряд — это нарушение rate-limit).
- **UI:** список точек на сеть в городе; ключи графиков, отметок и карточек
  включают код точки (иначе отметка точки А будет видна на карточке точки Б);
  агрегат по сети — «от … до …» и число точек, а не среднее.

**Решено по существу (не вопросы):**
- Пятёрка: максимум одна точка на город, лишние `ready: false` — сеть отдаёт
  магазин по IP, подмену проверить нечем.
- Breaker и `poll_meta` не трогаем по смыслу: пауза остаётся на сеть, а метка
  последнего опроса — одна на **город** (`poll_meta` ключуется городом, а не
  сетью), иначе пауза размножит трафик, а метка начнёт врать про весь город.
- Полки: решается вместе с миграцией маркеров — per-точка (повторять раскладку
  N раз) или per-сеть (проще, но раскладка едет между точками).

**Решения владельца, шесть открытых вопросов закрыты:**
1. **Список точек — руками в `catalog.ts`.** Нового механизма добавления нет.
2. **Показ — все точки сразу галочками**, а не переключатель: сравнение цен
   между точками и есть смысл фазы.
3. **Подпись точки — адрес из сети** (берется из ответа, колонка
   `stores.address` уже есть). «№2» только если адрес не пришёл.
4. **Избранное и автоопрос идут по всем точкам** сети в городе: товар,
   подешевевший во второй точке, иначе не всплывёт. Точки одной сети
   опрашиваются с паузой между запросами (`SAME_STORE_POINT_PAUSE_MS`, иначе
   два запроса уходят в один домен подряд).
5. **Агрегат при расхождении цен — «от … до …» плюс число точек.** Среднего
   не показываем: среднее двух магазинов — число, которого нет ни в одном.
6. **Полки — per-точка**, а не per-сеть: иначе «раскладка едет между точками»,
   то есть товар из точки А показывается в выдаче точки Б.

**Готово по подготовке:**
- **Найден способ получать коды точек.** У Магнита НЕТ списка магазинов ни в
  API, ни в sitemap: `/webgate/v1|stores`, `/shops`, `/stores` → 404,
  `/webgate/v2/cities` отдаёт 5182 города, но без кодов точек, sitemap содержит
  только разделы и товары. Зато при выборе магазина на сайте сеть сама зовёт
  `POST /webgate/v1/stores-facade/search` с географическим квадратом:
  `{"filters":{"geo":{"typeName":"box",leftTopPoint,rightBottomPoint},
  "deliveryTypeList":["DELIVERY_TYPE_PICKUP"],"storeTypeListV2":["MM"]}}`
  и получает все точки внутри. Ответ завёрнут в `items.items`. Адрес точки —
  `POST /webgate/v1/stores-facade/store` с её кодом.
- **Скрипт сбора:** `scripts/magnit-stores.ts` (`npx tsx scripts/magnit-stores.ts
  <город> --radius 0.04 --check 4 --addresses`). Опорная точка берётся из
  справочника, квадрат строится вокруг её координат, скрипт **сам себя
  проверяет** — код из справочника обязан найтись среди отданных точек. В
  `catalog.ts` не пишет ничего, только печатает коды и проверяет их живым
  поиском.
- **Живая пара для проверки фазы:** Питер, `277027` (Лиговский пр-кт, 271, стр. 1)
  и `673708` (ул Тосина, д 1 к 1 стр 1) — разные улицы и **разные цены**
  (89.99 против 109.99 на «молоке»), оба отдают товары. Соседние коды для
  следующих городов: Ульяновск `731274`, `731246`; Москва `322952`, `358543`.
- Замеры сбора: Москва ±13 км — 109 точек, Питер ±4 км — 32, Ульяновск ±6 км —
  47; опорный код находился во всех трёх квадратах.

### Порядок работ (план реализации)

Работа идёт по слоям снизу вверх, и каждый шаг оставляет проект в собираемом
состоянии с зелёным гейтом.

**Шаг 1. Контракты адаптеров, аддитивно и без смены поведения.** `storeCode`
появляется в типах цены и **заполняется кодом точки, о которой просили**, во
всех адаптерах и нормализаторах; база его пока не использует, поэтому поведение
не меняется и шаг безопасен.

Обязательным полем, а не опциональным: при `exactOptionalPropertyTypes`
опциональное поле позволило бы оболочке его не передать, и ключ молча станет
пустым — цена приклеится не к той точке.

**Что в шаге есть.** `PricePoint`/`ScrapedProduct`, девять мест сборки товара в
`src/`, константа `UNKNOWN_STORE_CODE` (`'?'`) и её единственное применение:
товар, прочитанный из базы по сети и городу, честно несёт «точку неизвестна».
Подставлять туда код из справочника нельзя — это эхо конфига: вторая точка в
городе получила бы чужой товар с чужим кодом, и на шаге 2 это уехало бы прямо в
ключ цены. Этот случай ревью поймало, и он был в первом варианте шага.

**Чего в шаге намеренно нет.** Контракты IPC — `api.ts`, preload,
`runScheduler({storeIds})`, `setCurrentStores`, `ShelfScope`, `Favorite`,
`getHistory`, `StorePrices`, `StoreCatalog`, `SchedulerStatus`,
`StaleStoreError.storeKey` — перенесены на шаг 4. Причина не в лени, а в том,
что их нечем наполнить: пока база не знает про точки, добавленное поле в
`runScheduler` ломает всех вызывающих (проверено на практике), а `searchPrices`
и `getCatalogs` всё равно не могут отдать две записи одной сети, потому что ядро
ещё не различает точки. Контракт без данных — это поле, которое всегда пустое,
то есть ложь в типах.

**Чем проверяется.** Утверждения о поле есть в каждой сети — Магнит (предложение,
карточка, плитки), Лента, Светофор, Пятёрка, Чижик, Перекрёсток — плюс
утверждение на sentinel в кэше полки. Тест, который проверял бы только
компиляцию, ничего не ловил: `src/shared/types.ts` вообще исключён из отчёта о
покрытии.
**Шаг 2. Миграция и переключение ключа — одним атомарным шагом.** Делить нельзя:
между «новой колонки» и «нового ключа» приложение тихо пишет историю в мусорную
линию `'?'`.

- `stores`: PK → `(id, city, external_store_id)`; сид переписывается на
  `ON CONFLICT(id, city, external_store_id)` — иначе SQLite отвергнет весь
  `exec(SCHEMA)` и `openDb` молча отдаст `database: null`.
- Новая колонка `store_code` в `prices_history`, `favorites`,
  `product_categories`, `product_category_manual`, **`poll_checklist`** и
  **`product_links`**. Последние две в первом варианте плана были пропущены, а
  обе несут идентичность точки: в `product_links` лежит `url` и `store_sku`, то
  есть без кода вторая точка затрёт первую, а полка вернёт товар чужой точки.
- `DROP INDEX IF EXISTS idx_prices_lookup` обязателен: `CREATE INDEX IF NOT
  EXISTS` оставил бы старое определение без кода точки.

**Порядок операций внутри пересборки таблиц — буквально такой:**
`PRAGMA foreign_keys = OFF` → `BEGIN` → пересборка таблиц и индексов →
`PRAGMA foreign_key_check` → если непусто, `ROLLBACK` и **громкая ошибка, а не
`database: null`** → иначе `COMMIT` → `PRAGMA foreign_keys = ON`.
Причина не теоретическая: `favorites` и обе таблицы раскладки несут `REFERENCES
products(id)`, а `openDb` включает `foreign_keys = ON` **до** `migrate()`. Одна
сирота при `INSERT ... SELECT` роняет FK, исключение пробрасывается наверх, а
`openDatabase()` его глотает — цены на экране есть, история, полки и избранное
мертвы. В существующей `migrateFavorites` это уже закрыто фильтром по
`products`, и пересборка обязана нести ту же защиту.

Миграция обязана быть **идемпотентной по форме** и корректно отрабатывать на
трёх состояниях: свежая база, старая форма, уже мигрированная. Иначе пересборка
повторится при каждом запуске — ровно тот баг, который чинили предикатом
`keyOk`.

**Бэкап до первой разрушающей пересборки**, через порт `AppStorage`, а не через
`node:fs` — иначе не переедет в Фазу 7, где база в памяти. `writeDb` при этом
переводится на tmp+rename: сейчас это `fs.writeFileSync` без атомарности.
Отдельное и важное свойство: миграция после `openDb` в файл не попадает, поэтому
прерванный процесс **не оставит на диске полумигрированную базу**. Опасность
обратная: первая же запись после миграции перезапишет оригинал, и откатить
пересборку `prices_history` будет нечем. Поэтому бэкап — часть релиза, а не
опция: откат версии без отката БД невозможен.

**Правило для sentinel `'?'` одно и обязательное: это только историческая
линия, никогда — цель опроса и никогда — элемент интерфейса.** Без этого
правила `listTrackedProducts` вернёт по две строки на каждый ранее отслеженный
товар, планировщик построит цель из каждой, `storeByCode(..., '?')` ничего не
найдёт, и товар навсегда останется в «не проверено» без единой ошибки.
Закрывается явно:
- `listTrackedProducts`: `WHERE store_code <> '?'`;
- `getPriceHistory`, `latestPrices`, полки из БД: код в `WHERE` обязателен,
  иначе `'?'`-линия склеится с реальной на одном графике — тот самый дефект,
  ради которого фаза и затевается;
- `'?'` исключается из числа точек и из min/max агрегата.

**`favorites` и `product_category_manual` размножаются по точкам**, настроенным
в `catalog.ts` для этой пары (сеть, город): решение владельца №4 требует, чтобы
избранное и автоопрос шли по всем точкам. Иначе порог не сработает никогда, а
ручная раскладка перестанет защищать товар и автораскладка его разложит заново.
`prices_history` **не** размножается: там правило «новая точка = новая
история» верно.

**Ретенция `prices_history` — до миграции.** Фаза 7 требует её до
пересборки таблицы, иначе та же пересборка делается дважды, а каждая — это
полный `export()` всей базы в памяти `sql.js`. Либо ретенция становится шагом 0,
либо решение фиксируется здесь же явно: «делаемо, но не в этой фазе», плюс
замер реального размера `prices.db`, потому что пересборка в памяти при большой
базе — это риск OOM в main.

**Гейт шага:** не `test-db`, а полный — `npm test` (`test:db-open`,
`test:services`, `test:scheduler`, `test:core-edges` трогают эти таблицы),
`npm run test:coverage:check` со 100 % по строкам и веткам (каждая ветка
миграции: свежая база / старая форма / уже мигрированная / нет `products` /
сироты) и `npm run gen:schema`: DDL пересборки в `db.ts` обязан совпадать с
`schema.sql`, иначе свежая и мигрированная базы разойдутся и предикаты формы
будут пересобирать таблицу каждый запуск.

**Шаг 3. Каталог точек.** `catalog.ts` учится держать несколько записей на
`(storeId, city)`: `storesForCity(city, storeId)` и `storeByCode(storeId, city,
code)`. Все `find(s => s.storeId === …)` заменяются поиском с учётом кода.
Смысла своя `stores` в БД не имеет — её не читает никто, кроме сида и двух
тестов.

**Шаг 4. Ядро.** `savePriceIfChanged`, `latestPrices`, `getPriceHistory`,
`listTrackedProducts`, `checkTargets`, `saveNotifiedPrices`, полки, `getHistory`.
Агрегация: `byStore` в `services.ts` сейчас ключуется по `storeId`, и две точки
одной сети слились бы в одну карточку — ключ становится `storeId + storeCode`.
Строки `CachedCategoryRow` и фильтры полок тоже несут код: пока фильтр
`.filter(r => r.storeId === …)` и `cached[0]` не по коду, полка вернёт смесь двух
точек, причём список возьмётся у произвольной. `classifyAndSave` пишет
раскладку одним кодом на всю пачку — при решении «полки per-точка» это
привяжет полку к одной точке.

**Сюда же перенесены контракты IPC** из прежней редакции шага 1: `api.ts`,
preload, `runScheduler({storeIds})`, `setCurrentStores`, `ShelfScope`, `Favorite`,
`getHistory`, `StorePrices`, `StoreCatalog`, `SchedulerStatus.counts`,
`StaleStoreError.storeKey`. Их нечем наполнить раньше: пока база не знает про
точки, `searchPrices` и `getCatalogs` не могут отдать две записи одной сети, а
добавленное поле в `runScheduler` ломает вызывающих. Ставить их надо там, где
ядро уже различает точки, иначе это поле, которое всегда пустое.

**Шаг 5. Адаптеры и сессии.** Подтверждённый сетью код едет в ответе, а не из
конфига: `storeItems` намеренно перебивает `storeId`/`city` на опрашиваемую
сеть, и это правильно, но **код перебивается тем же способом** — иначе
подтверждение потеряется по дороге. Расхождение с настроенной точкой — громкая
ошибка без записи: инвариант «успешный HTTP ≠ наш магазин» обязан работать и на
коде точки.

Ключи сессий Ленты (`sessions`, `inflight`) становятся `city:storeId` — иначе
две точки дерутся за одну сессию. Правкой ключей мало: guard ретрая 401/403 и
сигнатуры `session`/`createSession` тоже per-point, иначе после частичной
правки Лента умирает до перезапуска процесса.

Подпись точки — адрес из сети (решение №3), но **ни один адаптер адрес сейчас
не отдаёт**: у Магнита он живёт в отдельном запросе `stores-facade/store`. Значит
это отдельный запрос на точку плюс кэш, и такой шаг в плане нужен: `CityStoreInfo`
получает `address?`, а `stores.address` из БД не читает никто.

**Шаг 6. Склейка.** `matching.ts` перестаёт дедуплицировать по `storeId`: у двух
точек одной сети `canonicalId` совпадает, и второй offer уходит в `continue` —
сравнение между точками физически не отобразится. Ключ группы становится
`storeId:storeCode:canonicalId` — он же React-key и ключ кэша истории в
renderer'е. `sameProduct` и `normalizeName` не трогаем.

**Шаг 7. Опрос.** Цель — `(canonical, store, city, code)`. Точки одной сети идут
последовательно с паузой **между** точками. При этом чередование городов в
`scheduler.ts` обязано сохраниться: порядок «без сортировки» там намеренный, он
не даёт прогревать браузер на каждом переходе. Группировка по точке без этого
удвоит прогрев у Пятёрки и Чижика, а у Чижика ещё и упрётся в лимит сессий — две
точки одной сети это две сессии Firefox.

**Шаг 8. UI.** Список точек сети в городе — галочками, подпись — адрес из сети.
`Record<storeId, boolean>` в renderer'е на две точки даёт одну галочку, значит
выбор становится по паре «сеть + код». Ключи графиков, отметок и карточек
включают код точки, иначе отметка точки А будет видна на карточке точки Б.
Агрегат при расхождении цен — «от … до …» и число точек. Отдельно: фильтр
«найдено в N и более сетях» считает `new Set(offer.storeId)` — две точки одной
сети не должны превращать одну сеть в две.

**Порядок не переставляется:** контракты → миграция с ключом → каталог → ядро →
адаптеры → склейка → опрос → UI.

**Старая сборка на мигрированной базе.** Её сид с `ON CONFLICT(id, city)` станет
невалидным, `exec(SCHEMA)` упадёт, а `openDb` отдаст `database: null` — то есть
на экране цены есть, а история, полки и избранное мертвы. При этом файл базы
старым билдом **не перезапишется**: persist там не вызывается, то есть каскадного
ущерба нет. Значит порядок выпуска: релиз с миграцией выходит с отключённым
автообновлением на один релиз, в release notes и баннером в UI пишется про
миграцию, а бэкап-файл остаётся единственным способом отката.


## Фаза 5 — Ядро вне Electron

Цель: чтобы ядро (адаптеры, БД, планировщик, матчинг, бизнес-логика) работало
без Electron и без `node:fs`, и вторая оболочка была возможна без дублирования
кода. Порядок работ:

1. [x] **Схема БД в сборке** — см. Фазу 0. Необходимое условие: пока ядро читало
   файл с диска, второй оболочке было нечего переиспользовать.
2. [x] **Порты платформы** (`src/core/platform.ts`): хранилище БД, JSON-хранилище
   кэша витрин, версия/уведомление/внешняя ссылка, фоновые таймеры, лог,
   `process`-читалка. Реализации: `electron/node-platform.ts` (Electron) и
   `electron/node-files.ts` (только fs, чтобы тесты под tsx не тянули Electron).
   `electron/main.ts` сжался 595 -> ~190 строк: окно, 23 канала IPC, автообновления,
   жизненный цикл, `EXTERNAL_ALLOW` и `close5kaBrowser` — всё это осталось в
   оболочке сознательно.
3. [x] **`src/core/services.ts`** — вся бизнес-логика: `searchPrices`,
   `getCatalogs`, `getCategoryProducts`, `getOurCategories`, `getOurCategory`,
   `getHistory`, планировщик. Запуск таймеров вызывает оболочка, ошибки летят
   через `emit` в `webContents.send`.
4. [x] **Переезд `src/main` -> `src/core`** — глубина импортов сохранилась,
   обновлены внешние ссылки: `electron/main.ts` и порты, 10 скриптов,
   `tsconfig.electron.json`, README, `.opencode/rules.md` и доменный скилл
   (иначе источники правды указывали бы в пустоту). Попутно `build:electron`
   теперь чистит `dist-electron` перед `tsc`: иначе после переезда в
   electron-builder уехал бы мёртвый `src/main/**` из прошлой сборки.
5. [x] **Тест «ядро без Electron»** (`npm run test:core` (файл `scripts/test-core.ts`), первый в цепочке) —
   `createCore` с фейк-адаптером и хранилищем в памяти плюс статический guard:
   в `src/core/**` и `src/shared/**` запрещены импорты `electron`, `node:*`,
   динамический `import('node:…')` и `require`, а `process.*` читается только в
   `platform.ts`. Guard сработал на реальной связности: `electron-log` в
   планировщике, `node:crypto` в адаптере Ленты, `process.env` у 5ka.
6. [x] **Убрана связность вне портов**: `electron-log` -> `CoreLogger`,
   `node:crypto randomUUID` -> `globalThis.crypto`, `process.env` -> `readEnvFlag`
   (опциональный глобал: в Android `process` не существует и чтение не должно
   ронять ядро). Playwright остаётся fail-loud и в Android-сборке не работает —
   это известное ограничение, не баг.

Правки этого шага (все закрыты):
- пустой кэш витрины считался попаданием и блокировал сеть на TTL 7 суток;
- упавший опрос рапортовался как успешный («всё хорошо» при мёртвой БД) — теперь
  `lastError` + счётчик провалов подряд и отдельный текст summary;
- ошибка открытия БД уходила только в лог, хотя цены на экране есть, а в
  истории пусто — теперь она в `error` у каждой записи;
- ключ истории брался из ответа адаптера, а не из опрошенной сети: цена и
  раскладка могли разъехаться по разным `store_id`;
- `classifyAndSave` писал раскладку по всем товарам пачки, включая не
  записанные в `products`: FK откатывал транзакцию и терял раскладку целиком;
- «Не разложено» при недоступной БД выглядело как «товаров нет»;
- `openDb` отдавал чужую базу, если его звали с другим хранилищем;
- `electron/main.ts` вызывал `app.getPath` на верхнем уровне модуля, до
  `whenReady` — ядро теперь собирается после готовности приложения.

Capacitor как вторая оболочка — следующий этап: сетевой слой на нативном HTTP,
фоновый опрос через WorkManager, тот же `window.api` для renderer'а. Подробности
ограничений — в «Возможно в будущем».

## Возможно в будущем
- Экспорт истории в CSV.
- Android-приложение. Ограничение, измеренное 2026-09-29: сеть **не
  открывает CORS**. На preflight `OPTIONS /jrpc/searchItems` — 200 без
  `Access-Control-Allow-Origin`, на реальном запросе с чужим `Origin` — 200 с
  данными, но тоже без ACAO (значит браузер/WebView их не отдаст в JS), а
  `GET catalog/items/{id}` с чужим `Origin` меняет ответ с 401 на 403. То
  есть PWA и голый WebView не подходят: сетевой слой должен быть нативным
  (OkHttp в Capacitor) либо жить в Node-подобном рантайме. Плюс два
  ограничения WebView: фоновый опрос цен (нужен WorkManager или foreground
  service) и Playwright-фолбэк Пятёрочки (на Android движка нет). Отсюда
  порядок работ: сначала вынести ядро (адаптеры, матчинг, БД, планировщик) из
  Electron в платформенно-независимый слой — работа нужна и самому Electron,
  и как отдельный тестовый каркас.

- Серверный бэкенд для опроса магазинов. Пока приложение только локальное:
  цены, история и избранное лежат в `prices.db` на диске, никуда не уходят.
    Перенос именно опроса (не данных) возможен, когда появятся причины:
    свой круглосуточный компьютер, к которому надо подключить телефон, или
    общий доступ к ценам. Обязательное условие — движок до сих пор не тащит
    Electron и `node:fs` (Фаза 5): вторая оболочка должна уметь и опрашивать
    сети, и писать ту же БД. Плата за решение: анонимные запросы к сетям
    пойдут с чужого IP, поэтому rate-limit и риск бана антифрода ложатся на
    сервер, а не на домашний компьютер.

## Не делаем
- Обход капч сервисами (только ручное решение + пауза).
- Платная подпись exe (личное использование, достаточно unsigned + portable).
- Публичный SaaS на чужих данных (ToS сетей, личное использование).

## Разбор Пятёрки: категория не открывалась (1.2.0)

Пользователь увидел «сайт не определил магазин — скорее всего капча/антифрод».
Живой разбор показал, что капчи нет, а диагностика врала по двум причинам:

1. **Matcher каталога без правой границы.** `/categories` совпадает и со
   списком товаров `/categories/<id>/products`, а тот запрос сайт делает
   уже на главной. Мы перехватывали его и разбирали как дерево категорий →
   «категории пусты (смена вёрстки?)». Правка: правая граница `(\?|$)`.
2. **Кука магазина как признак готовности.** Кука `5ka_store_id_store`
   ставится не сразу (в одном прогоне её не было через 6 с), но магазин при
   этом уже известен — X5 называет его прямо в URL запроса каталога. Кука
   теперь приоритет, код из каталога — подтверждение и фолбэк.

Попутно найдено и исправлено: отвергнутая сессия браузера оставалась в
`inFlight`, и одна ошибка убивала сеть Пятёрки до перезапуска приложения —
ровно тот симптом, с которого начался разбор. Путь товара тоже требовал куки и
теперь сверяется так же. Живая проверка после правок: 40 категорий с
картинками, 12 товаров в «Молоко, сливки», карточка товара отдаёт цену.

Сверка магазина Магнита в Playwright-путях (`search`, `fetchCategoryProducts`)
была только по эху куки — это доказывало, что кука дошла, а не что магазин тот.
Добавлена сверка по `href` карточек (`assertCardsOwnStore`); при отсутствии
code в ссылках — громкая ошибка вместо тихого пропуска.

## Фаза 7 — Android (этапы 0а и 0б сделаны, развилка решена)

Задача: то же ядро цен на телефоне. Ядро уже отделено от Electron (`src/core` не
знает про окно), поэтому переносится переиспользованием, а не переписыванием.

**Про вид: это НЕ та же вёрстка, уменьшенная до ширины телефона.** Мобильный
экран — палец, а не мышь, и вертикаль места не прощает. Что это значит на
практике (зафиксировано 2026-11-11, до начала работ, чтобы не потерять):

- **Один столбец карточек и сетка фильтров внизу, а не сбоку.** На десктопе
  фильтры стоят строкой над выдачей; на телефоне та же строка съест треть
  экрана, поэтому фильтры сворачиваются в панель, а не прячутся.
- **Никаких hover-эффектов и мелких кеглей ниже 14 px** — палец не наводит.
- **Подвал с кнопкой опроса и версией перестаёт быть подвалом** и уходит в
  плавающую панель или в меню: на телефоне он в самом низу и не виден при
  прокрутке выдачи.
- **Горизонтальная прокрутка строк запрещена**, а таблица истории цены
  превращается в вертикальный список замеров.
- Цвета, радиусы и иконки полок остаются теми же — фирменный вид должен
  узнаваться, различается раскладка, а не палитра.

**Замер CORS по всем шести сетям, телефонная UA, чужой Origin:**

| Сеть | Preflight | Реальный запрос | Итог для WebView-JS |
|---|---|---|---|
| Магнит | 200 **без ACAO** | 200 без ACAO | ответ не отдаст в JS |
| Лента | 200 **без ACAO** | 200 без ACAO | ответ не отдаст в JS |
| Светофор | 200 **без ACAO** | 200 без ACAO | ответ не отдаст в JS |
| Чижик | 200 без ACAO | 403 + ACAO | WAF, и preflight без ACAO |
| Пятёрка | 200 + ACAO | 403 + ACAO | ACAO есть, но WAF |
| Перекрёсток | 200 + ACAO | 403 + ACAO | ACAO есть, но WAF |

Вывод, который определяет всю Фазу 7: **обычный `fetch` из WebView не годится
ни одной сети.** У трёх нет ACAO вовсе, у трёх WAF. Значит сетевой слой обязан
быть нативным (Capacitor HTTP) — тогда CORS не применяется вовсе, и мы упираемся
уже не в браузерную политику, а в саму сеть.

Что это значит по сетям при нативном HTTP (тот же запрос, что у нас в Node):
- **Магнит** — прямой `fetch` с кукой магазина работает (0.6–2.2 с живой замер).
- **Светофор** — статический JSON-прайс точки, обычный GET.
- **Лента** — `/jrpc/searchItems` с `SessionToken`, работает из Node.
- **Пятёрка, Чижик, Перекрёсток** — держатся на запросе ИЗ КОНТЕКСТА СТРАНИЦЫ
  (WAF режет всё остальное). В нативном слое страницы нет. Единственный
  возможный путь — второй WebView, загруженный на origin самой сети, и запросы
  из него. Это отдельный прототип с честной оценкой: у нас нет ни кода, ни
  замера, что такой путь вообще жизнеспособен на Android.

**Что уже переносится без правок (замер структуры):** в `src/renderer/**` нет ни
одного импорта `electron`, `node:*` или `require` — 56 обращений к `window.api`
и всё. То есть renderer портируется заменой моста, а не переписыванием.

**Первый шаг фазы (не код адаптеров, а замер):** прототип Capacitor с нативным
HTTP на Магните. Он отвечает на главный вопрос фазы — работает ли вообще нативный
HTTP с нашими заголовками и куками — и стоит существенно дешевле, чем писать
второй WebView вслепую.

**Что придётся решить по дороге:** сборка под Android вместо NSIS-установщика,
уведомления вместо `shell.notify`, фоновый опрос вместо таймера окна,
и то, чем заменить `window.api` — границу IPC. Подробный план с разбором
Capacitor — ниже, в этой же фазе.

**Инструменты на машине (эмулятор поднят и проверен).**
Источник — соседний проект `VK-Fork`, где это уже решено: там Android-приложение
на Kotlin собирается gradlew и разбирается на эмуляторе AVD `vktest`.
У нас на машине: **Java 21**, **Android SDK** в `%LOCALAPPDATA%\Android\Sdk`
(platform-tools с `adb.exe`, platforms 34 и 37, build-tools 34 и 36, emulator,
cmdline-tools, system-image **android-34**), AVD **`vktest`** (android-34,
x86_64). Поднят headless (`-no-window -no-audio -gpu swiftshader_indirect`),
`adb devices` видит `emulator-5554`, Android 14, x86_64, WebView в системе есть.

Вывод: **этапы 0а и 0б можно мерить прямо здесь, без телефона владельца.**
Отдельного Gradle в PATH нет — он приедет вместе со сборкой Android-проекта, а
для замеров 0а/0б он и не нужен.

**План этапов (принят на пре-ревью и переписан по его замечаниям).**
Критик вернул первый вариант с четырьмя P0, и все четыре оказались по делу: в
плане были неверны факты о собственном репозитории.

*Что в первом варианте было неверно:*

  `persistDb` во всех местах.
- **Пятёрка на Chromium мертва**: транспорт режет даже headful Chromium, весь
  браузерный слой репозитория работает на `pw.firefox`. Чижик и Перекрёсток на

**Этап 0а — СДЕЛАН, замер прошёл на эмуляторе.** Собран минимальный проект
Capacitor в `.agent/cap`: веб-часть собирается esbuild'ом из настоящего кода
репозитория, Android-платформа добавлена через `cap add android`, APK собран
gradlew, поставлен на эмулятор `vktest` и запущен. Звонится **настоящий**
`MagnitAdapter` — никакого рукописного `fetch`.

Что показал замер (лог WebView через `adb logcat`):
- `мост Android: object` и `плагин CapacitorHttp: object` — и то, и другое на

- `search: 21 товаров за 3818 мс` — живые данные Магнита пришли через нативный

  https://magnit.ru/product/1051242602-...` — **адрес ответа доехал**, а значит
  сверка «тот ли магазин» в Магните прошла. Ровно та проверка, которая без

- `карточка: Молоко детское Агуша ... | 64.49 | за 1646 мс` — `fetchProduct`

Тот же товар и та же цена, что и на десктопе при живом запросе (Агуша, 64.49):
идентичность цены между платформами подтверждена. Остаток чек-листа (User-Agent,
204 без тела) на живых ответах не всплыл — 204 в этом запросе не встретился.

**Этап 0 — замеры, кода продукта нет.** Оба шага выполняются ДО любой переделки,
потому что отвечают за ценность всей фазы.
- **0а. Нативный HTTP через настоящий путь адаптера.** Минимальный проект
  Capacitor, в котором импортируется `MagnitAdapter` и зовётся `search()`
  НАСТОЯЩИМ кодом, а не рукописным `fetch`. Проверяем: патчит ли Capacitor
  `globalThis.fetch` (тогда контракт `StoreAdapter` не трогаем вообще), работает
  ли `AbortSignal.timeout`, `res.text()`, поведение на 403, и не мешает ли
  cookie-jar Capacitor явному заголовку `Cookie:` из `magnit.ts:598` (нужен
  `enabledCookieHandling: false` — иначе чужой cookie смешается с нашим и
  инвариант «успешный HTTP ≠ наш магазин» треснет).
- **0б. Второй WebView на origin сети.** По одному замеру на Чижика и
  Перекрёстока (Chromium, не Firefox). Пятёрку не меряем — она мертва по замерам
  репозитория.

**Результат 0а (код Capacitor 8.5.3 разобран, все ссылки — на
установленный `@capacitor/android`, замер продолжается на эмуляторе).** Проверять
было нечего: плагин **патчит `window.fetch` сам**, и это меняет план в нашу пользу.
- `native-bridge.js:436-469` — оригинал сохраняется в `win.CapacitorWebFetch`,
  дальше `window.fetch = async (resource, options) => {...}`. То есть адаптеры
  продолжают звать `fetch`, и на Android он прозрачно становится нативным запросом
  без CORS.
- **Патч выключен по умолчанию.** `native-bridge.js:461-466` спрашивает
  `CapacitorHttpAndroidInterface.isEnabled()`, а тот читает
  `pluginConfig.getBoolean("enabled", false)` (`CapacitorHttp.java:85-87`).
  Без `"plugins": { "CapacitorHttp": { "enabled": true } }` в
  `capacitor.config` патча не будет и CORS останется. Это обязательная строка
  конфига, а не опция.
- Два пути: GET/HEAD/OPTIONS/TRACE переписываются в
  `<serverUrl>/_capacitor_http_interceptor_?u=<реальный url>` и уходят обычным
  web-fetch, который перехватывает `WebViewLocalServer.shouldInterceptRequest`
  (`Bridge.java:288`); POST и прочие идут через
  `cap.nativePromise('CapacitorHttp', 'request', ...)`. Запросы на адрес самого
  приложения мимо прокси не идут (`native-bridge.js:480`).
- **Cookie-меша не будет.** Нативный обработчик не подмешивает cookie-jar, наш
  заголовок уходит как есть: `connection.setRequestHeaders(headers)`
  (`HttpRequestHandler`). Оговорка `enabledCookieHandling: false` из первого
  варианта плана на Android не нужна — это забота iOS/CapacitorCookies.
- **Вывод: контракт `StoreAdapter` не меняется, HTTP-порт в ядре не нужен.**
  P0 критика №2 снят в нашу пользу — правок в `src/core/adapters/` не требуется.

**Новый риск, найденный при разборе (в плане его не было).** `AbortSignal` на
нативном пути **не поддерживается**: обработки `signal` в патче нет, отмены в
плагине тоже, таймауты существуют только как опции `connectTimeout`/`readTimeout`
в миллисекундах. А `AbortSignal.timeout` стоит в **9 местах** адаптеров, и POST
ровно там, где таймаут критичен: Лента — четыре POST, Магнит — прямой POST,
Перекрёсток — POST. Значит на Android висящий запрос
может висеть без предела. Прежний «retry с бюджетом 30 с» на телефоне не сработает
и должен опираться на явные таймауты.

**Решение найдено, область оказалась узкой.** Таймауты нативного
плагина задаются прямо в вызове: `call.getInt("connectTimeout")` и
`call.getInt("readTimeout")` (`HttpRequestHandler.java:390-391`), это настоящие
таймауты ОС — соединение реально рвётся, а не просто отклоняется промис. Просто
у patched `fetch` их задать нельзя: в нативный вызов уходит только
`{url, method, data, dataType, headers}` (`native-bridge.js:526-532`), ни
`signal`, ни таймаут. Значит для POST нужен прямой вызов плагина.

**Масштаб правки — пять мест, а не девять.** POST есть только у Ленты, и весь её
сетевой код проходит через одну функцию `LentaAdapter.request`, где
единственный вызов `fetch` обслуживает и GET, и POST. Прямой путь Магнита,
Светофора и Пятёрки — это GET, но переведены не все: Магнит тоже пошёл через
хелпер, и вот почему. Встраиваемые транспорты (`chizhik-browser.ts:193`,
`perekrestok-browser.ts:158`) зовут `fetch` внутри страницы Firefox — это наш
Playwright, к Android WebView отношения не имеет.

**Почему Магнит тоже переведён.** Он единственный читает `res.url` для сверки
магазина (`magnit.ts` — проверки «ушёл с `/product/`» и «ушёл с `magnit.ru`»).
Нативный слой не кладёт адрес в конструктор `Response`, так что прямой `fetch` на
Android вернул бы пустой адрес и сверка упала бы на живом ответе. `httpFetch`
прокидывает адрес через `Object.defineProperty` — так же делает и сам патч
Capacitor. Без этого Магнит на телефоне отвалился бы целиком. Светофор и Пятёрка
адрес не читают, поэтому оставлены на обычном `fetch`.

**Ложный потолок, который чуть не попал в план.** Первый вариант опирался на
«Capacitor ограничивает GET тридцатью секундами». Это не так: единственные
`setReadTimeout(30 * 1000)` в `WebViewLocalServer.java:539-540` стоят в
`handleProxyRequest` — это прокси HTML для live-reload. Нативный HTTP из патча
обрабатывает `handleCapacitorHttpRequest`, где соединение собирается вообще без
таймаутов. Потолок для GET — наш собственный `AbortSignal`, и то лишь потому, что
патч не выбрасывает `options`. Сам нативный запрос при отмене не прерывается.

**Что сделано:** новый `src/core/http.ts` — на обычной платформе это нынешний
`fetch` с `AbortSignal.timeout`, на нативной прямой вызов `CapacitorHttp.request`
с явными `connectTimeout` и `readTimeout` и сборкой `Response`. Переведены пять
вызовов: один в `lenta.ts` и четыре в `magnit.ts`. Определение среды — по
мосту Android, он вынесен в `platform.ts` как `isNativeShell()`, потому что там
уже объявлено единственное допустимое место чтения окружения. Плагин ищется
только внутри нативной ветки: в веб-сборке Capacitor тоже есть, но там его
сетевой плагин — обычная обёртка над `fetch`, которая наши таймауты съедает.
Тесты в `scripts/test-http.ts` (10 штук), покрытие файла 100 %.

**Откат на web-fetch на нативе запрещён** — ревью справедливо указало, что второй
такой POST ушёл бы в сеть без таймаута и без возможности отмены, то есть ровно
то, ради чего модуль написан. Ошибка натива пробрасывается наружу, её посчитает
защита сети. Если нативная среда есть, а плагина нет — внятная ошибка с подсказкой
про импорт `@capacitor/core` и `npx cap sync`. Флаг
`plugins.CapacitorHttp.enabled` на наш прямой вызов не влияет: он включает патч
`window.fetch`, а мы зовём плагин напрямую. По Android cookie-jar тоже нечего
выключать — обработчик собирает соединение из наших заголовков и своего ничего
не подмешивает.

**Потолок нужен на запрос целиком, а не на connect и на каждое чтение.**
`connectTimeout` и `readTimeout` не спасают от сервера, который отдаёт байт каждые
20 секунд: он держит опрос открытым бесконечно. Поэтому нативный путь ограничен
общим таймаутом сверху, как `AbortSignal` на десктопе. Само нативное соединение
при этом не рвётся — освобождается вызывающий, ровно как при отменённом GET.

**Чек-лист замеров на эмуляторе, кроме таймаута:**
- `CapacitorHttp` доступен — иначе `http.ts` остановится с внятной ошибкой, и
  это надо поймать первым делом;
- фактический `User-Agent` в логе нативного запроса. Лента его шлёт сама
  (`lenta.ts:447`), а нативный слой подставляет свой, только если заголовка нет
  (`HttpRequestHandler.java:410-412`), так что пункт снят — но сверяем, что
  пришёл именно наш, а не `Dalvik/...`;
- `Response` для 204/205/304 собирается с пустым телом: конструктор запрещает
  тело у этих статусов и бросает TypeError. В тестах закрыто;
- адрес ответа доезжает: натив не кладёт его в конструктор, а сверка «тот ли
  магазин» в Магните идёт по нему, поэтому `res.url` прокидывается вручную.
  Без этого Магнит падает на живом ответе;
- редиректы: `fetch` на десктопе ходит между протоколами, а `HttpURLConnection`
  нет. Эндпоинт с редиректом http→https на телефоне вернёт 3xx там, где на
  десктопе был ответ. Для наших сетей не подтверждено, но знать надо;
- отменённый нативный GET не рвёт соединение, поэтому «бюджет повтора» Магнита
  может добить новый запрос поверх ещё живого предыдущего. Лишний удар по сети,
  и на живом опросе это видно как двойные запросы к сети.

**Этап 0б — СДЕЛАН, развилка решена: Chromium обе сети режет.** Android WebView

## Фаза 7б — GeckoView: Firefox-движок внутри приложения

**Зачем.** Замер 0б показал, что Пятёрку, Чижик и Перекрёсток режет Chromium: тот
же код под Firefox отдаёт живые данные. Android WebView — это Chromium, а
Firefox-движка в системе нет. Единственный способ принести Firefox в
приложение — **GeckoView**, библиотека Mozilla: движок Firefox, встраиваемый в
любое Android-приложение.

**Координаты артефакта:** `org.mozilla.geckoview:geckoview`, репозиторий
`https://maven.mozilla.org/maven2`. Короткое «158.0» не резолвится, нужна версия
целиком.

**Что мы покупаем, если ветка выживет.** На десктопе все 6 сетей уже работают
через `pw.firefox`. На телефоне мы покупаем **ровно 2–3 сети** — ценой размера APK
и отдельного транспорта. Это критерий взвешивания в 7б.3.

**Честная часть.** Даже если GeckoView пройдёт, это не «ещё сети»: адаптеры говорят
на `pw.firefox` (context, page, `waitForResponse`, `route`), а GeckoView — не
Playwright. Впереди отдельный транспорт и вес APK. Поэтому ветка разбита так,
чтобы **потратить минимум на отказ**.

### Этап 7б.1 — spike: ПЕРВАЯ ИТЕРАЦИЯ СДЕЛАНА

Одностраничное приложение с GeckoView в `.agent/gecko/`, вне `android/`, со
своим `settings.gradle`, ноль правок в `package.json` и `capacitor.config`.
Протокол замера — `.agent/gecko/evidence.md`.

**Таблица 3×2, в те же минуты и с одного IP** (эмулятор выходит в сеть через
NAT хоста):

| Сеть | GeckoView | Firefox (контроль) |
|---|---|---|
| Чижик | **403 Forbidden** | 11 из 11 городов, 18–21 товар |
| Перекрёсток | каталог загрузился | 100 товаров |
| Пятёрка | главная загрузилась | магазин 35XY найден |
| контроль | Example Domain 200 | — |

**Чижик — исход «нет, не движковый блок».** Под GeckoView 403, под Firefox живые
данные с того же IP. Значит дело не в Chromium: Чижик режет и Firefox на Android.
Возможные причины — мобильный профиль движка, отсутствие накопленной сессии,
отпечаток TLS этой сборки. Патчить запрещено ToS, поэтому **Чижика можно
выносить из ветки уже сейчас.**

**Перекрёсток и Пятёрка — прошло только первое звено.** Документ открылся там,
где Chromium его резал, но документ не критерий: под Chromium `5ka.ru` отдаёт
200 при мёртвом каталоге. Вердикт пока **«API 200 не подтверждён»**, а не «да».

**Побочные результаты, оба важны:**
- **APK — 97 МБ на один ABI x86_64.** Для arm64 тот же порядок. Это вес, который
  пойдёт в 7б.3, и он уже заметный.
- **GeckoView роняет эмулятор на дефолтной памяти** — adb перестаёт отвечать.
  С `-memory 4096` работает устойчиво. Риск из плана подтвердился: под Фазу 7 с
  heap 256 МБ нужен второй AVD.
- **Сборочная линия:** GeckoView 158 требует compileSdk 37 и AGP новее 8.9;
  версия 147 идёт на compileSdk 36 и AGP 8.9.1. Для проверки «проходит ли
  движок» версия не важна, поэтому взята 147.

**Уборка.** `geckoview-config.yaml` и `am set-debug-app` не использовались,
настройки движка стоковые — убирать нечего.

### Этап 7б.2 — СДЕЛАН (2026-10-19): перехват свой, а не штатный

Штатного перехвата в GeckoView НЕТ: в классах версий 147 и 158 нет ни
`GeckoSession.WebRequestDelegate`, ни `setRequestDelegate`, ни `evaluateJS`
(проверено по AAR `org.mozilla.geckoview:geckoview`). План «включить перехват
`onFetch`» опирался на несуществующий API, поэтому замер сделан ИНАЧЕ — своим
инструментом `scripts/net-log-proxy.mjs` (локальный MITM-прокси: свой CA +
листовой сертификат, `scripts/make-proxy-ca.mjs`).

Что измерено (протокол — `.agent/gecko/evidence.md`):

- **Нативно из приложения Пятёрка и Перекрёсток режут (403 + WAF), контроль
  200.** Значит, «просто взять API напрямую» (как с Магнитом через webgate) для
  них не работает: сеть режет по профилю клиента, а не из-за CORS. Движок нужен.
- **Чижик отсеян окончательно:** 403 и под GeckoView, и под Firefox (ToS
  запрещает патчить).
- **Под GeckoView документы Пятёрки и Перекрёстка грузятся** (настоящие
  заголовки), но статус **API-запроса** не подтверждён — перехвата в движке нет.
  Это и есть то, что закрывать дальше: если API под движком тоже отдаёт 200 с
  разбираемым payload — ветка живая и дальше строится транспорт; если нет, то и
  движок не помогает.

Свой перехват (проверен на живом трафике) показывает и то, чего не видит
движок: метод, тело запроса, статус и начало тела ответа — по эмулятору и по
десктопу.

### Этап 7б.3 — размер и решение

Сборка с `arm64-v8a`, реальный вес APK, взвешивание против оставшихся сетей,
решение: тащить ли движок в релиз.

**Рамки ToS на весь остаток ветки.** Только стоковый GeckoView с дефолтными
настройками. Запрещены подмена UA и отпечатка, патч TLS/JA3, обход CSP/SRI,
решение капч. Конфиг-файл движка и удалённая отладка — только для замера, в
релиз не идут. Куки и токены — только в `.agent/`, в фикстуры не попадают.
Паузы ≥2 с между запросами, не больше 2 попыток на адрес, стоп после двух отказов.

**Лицензия.** GeckoView — MPL-2.0 плюс ограничения товарного знака Mozilla.
Для проекта с лицензией PAL v1.0 совместимо (MPL-2.0 — file-level copyleft,
в дистрибутив Android она не попадает), но нужна запись о стороннем коде, а
слово «Firefox» в UI и README писать нельзя.

Ничего из этого не трогает рабочую Фазу 7 на трёх сетях: spike живёт в
`.agent/gecko/`, APK лежит в `build/apk/` (в `.gitignore`), в гита не попадает и
в приложение не встраивается.

## Фаза 7в — Пятёрка на Android через «страницу-читалку» (verify пройден)

**База.** Измерение 5 (`.agent/gecko/evidence.md`): WebView ставит антибот-куки
5ka (`spid`/`spjs`); нативный запрос с ними — 403; XHR из страницы — CORS;
«открыть адрес API как страницу и прочитать тело» — единственный живой путь,
повторяющий десктопный приём Playwright. GeckoView отвергнут (перехвата и
`evaluateJS` в 147/158 нет). Зонд пункта 4 доработан и пересобран: штатный UA
(без подмены, это требование пре-ревью), `LOAD_NO_CACHE`, опрос DOM каждые 20 с
до 5 минут независимо от `onPageFinished`, полный жизненный цикл в логе
(`.agent/gecko/app/src/main/java/ru/pa/geckoprobe/MainActivity.java`).

**План (исправлен по пре-ревью — 3 P0 закрыты, P1 закреплены):**

1. **Нативный плагин `PageReaderPlugin`** в `android/app/src/main/java/ru/priceaggregator/`:
   скрытый offscreen WebView, чтение `document.body` **textContent** (не
   `innerText` — он зависит от layout, а панель не в иерархии), **с селектором**:
   `readPage(url)` возвращает текст тела для API-JSON; `readNextData(url)` ждёт
   непустой `#__NEXT_DATA__` (карточка 5ka живёт вшитой в него, а не в ответе
   API — `fetchProduct` обязан читать страницу товара, как
   `readProductFromNextData` в `5ka-browser.ts`). Оба метода: штатный UA,
   `LOAD_NO_CACHE`, опрос каждые 20 с до общего потолка, WAF-детект по тексту
   заглушки, все вызовы — на UI-потоке, чтения сериализуются (один глобальный
   CookieManager для всех WebView приложения), паузы ≥2 с между открытиями
   страниц, ≤2 попытки на адрес. `setContentView` приложению не мешает — панель
   не прикрепляется, как в зонде.
2. **Порт в ядре** (загрузчик, как у Playwright): инжектируемый page-reader,
   регистрируется ТОЛЬКО Android-мостом (`bootstrap.ts`), у Electron его нет —
   «страниц-читалка» там не нужна (есть Playwright). Громкая ошибка без
   регистрации, по образцу `playwright-port.ts:52`.
3. **Транспорт `src/core/adapters/5ka-page.ts`** — `StoreAdapter` поверх
   page-reader. v1: ТОЛЬКО `search` + `fetchProduct`; `fetchCategories` /
   `fetchCategoryProducts` — вне v1 (полки 5ka в телефоне не рисуются, как у
   Ленты — `categories.length === 0`). Эндпоинты — те, что сняты перехватом на
   десктопе (`5d.5ka.ru/api/catalog/v3/stores/{sap}/search?mode=store&
   include_restrict=true&q=…&limit=12`, `…/v4/stores/{sap}/categories?…`), sapCode 35XY вшит
   в открываемый URL. Режим `mode=store`: план писал их по одному перехвату с
   `mode=delivery`, но код (вслед за десктопным `pyaterochka.ts`) шлёт
   `mode=store` — и живой прогон Android подтвердил честный JSON: цена точки,
   а не доставки. `fetchProduct` открывает `https://5ka.ru/product/<plu>/`
   и ждёт `__NEXT_DATA__` через `readNextData`. Идентичность: sapCode задаём
   сами в URL (маркера в теле выдачи нет — как у Ленты), форма ответа сверяется.
   Нормализация — через существующий `5ka-parse.ts`.
4. **Идентичность ≠ «плагин отвечает»: v1-семантика.** При старте моста регистрируем
   5ka только если нативный плагин реально отвечает. КРИТИЧНО (пре-ревью): это
   проверка моста, НЕ того, что WAF пропускает страницы. Первый реальный
   опрос и есть verify — на отказ громкая ошибка и drain через существующий
   breaker. UI не обещает сеть заранее.
5. **Ленивый warmup.** Прогрев `5ka.ru` (~20–30 с) — не при старте приложения,
   а при первом обращении к Пятёрке; куки остаются в CookieManager, повторный
   прогрев по WAF-детекту (куки протухли). Нативный запрос с куками 403 — прогрев
   нужен только как донор браузерного контекста, не как источник заголовков.
6. **Порядок proof-loop:** spec-freeze (этот раздел) → build: `PageReaderPlugin` +
   порт + `5ka-page.ts`, гейты `npx tsc --noEmit`, `npm test`, **гейт Android:
   `npm run android:sync` + `cd android && gradlew.bat assembleDebug`** (Java
   без этой сборки не проверяется — пре-ревью P0-3); unit-тесты `5ka-page.ts` по
   образцу `scripts/test-android-platform.ts`: загрузчик не зарегистрирован →
   громкая ошибка; WAF-страница → throw; пустое тело → throw; двойное
   JSON-экранирование `evaluateJavascript` → полный JSON; `products: []` при
   живой сети → отказ деградации, не «пусто» — в фикстурах
   → evidence: живые замеры пункта 4 (эмулятор + телефон) ⇒ через **прод-плагин**
   и только со штатным UA (замер с подменённым UA пре-ревью не засчитывается);
   → verify: живой `search` Пятёрки на Android; → fix.
7. **Фон.** Чтение страниц работает только при живом процессе; в WorkManager-фазе
   Пятёрка в фоне честно станет «недоступной на этой оболочке» — как сейчас
   таймеры, это периметр Фазы 7, не баг фазы 7в.
8. **Тексты моста.** `installBrowser`/`browserStatus` в `bootstrap.ts` говорят
   «браузер на Android не нужен…» — с живым page-reader формулировка меняется
   (браузер заменён читалкой для Пятёрки, а не «сети не поддерживаются»).

**Что НЕ делает эта фаза:** не включает capability до живой проверки п.4; не
строит перехват ответов (shouldInterceptRequest не даёт тело без повторного
запроса — сборка ответа руками сломает антифрод-контекст); не патчит UA/отпечаток.

**Статус: verify пройден (2026-10-24).** Живые прогоны `scripts/live-android.ts`
на эмуляторе (vktest, android-34): скрипт говорит CDP напрямую нативным
WebSocket Node 22 (`Runtime.evaluate` к `window.api`) — Playwright
`connectOverCDP` отвергнут самим WebView («Browser context management is not
supported»). Первый `getPrices`: Пятёрочка 13 товаров (точка 35XY, первый
«Молоко Домик в деревне пастеризованное 2.5% 930мл» 99.99) при Магните 36 /
Ленте 12 / Светофоре 13, выдача целиком 125 с — в неё лёг WAF-челлендж прогрева.
Повторный прогон: те же блоки, 12.4 с — сессия антибота переживает вызовы,
ленивый warmup срабатывает один раз. Гейты: `npm run test:fast` — упало 0;
`tsc` по обоим конфигам чисто; `android:sync` + `assembleDebug` собираются.

**Финальная сборка (подтверждение 2026-10-24).** Тот же живой прогон на
финальном APK (PageReaderPlugin со всеми правками критиков + CSP android.html):
Пятёрочка 13 товаров, точка 35XY («Молоко Домик в деревне пастеризованное
2.5% БЗМЖ 930мл» 99.99), Магнит 36 / Лента 12 / Светофор 13; тёплый прогон —
3.5 с (сессия антибота переживает даже паузы между вызовами). Из отладочного
опыта: два ОДНОВРЕМЕННЫХ инстанса verify-скрипта к одному мосту дали
Пятёрочке честный PageFailure («тело ответа на поиск пустое») при живых
остальных сетях и полный цикл ~209 с — отказ выдержан самим каркасом, но
параллельный доступ к одной читалке сам гонит челлендж: верифицировать
одним инстансом.

Отличия от плана (замены по ходу отладки, не ревизия замысла):

- *Бюджеты выше плановых:* опрос DOM 2 с (план 20 с — DOM-опрос не ходит в сеть,
  чаще = точнее момент оседания), `PAGE_BUDGET_MS` 90 с и `WARMUP_BUDGET_MS`
  120 с: челлендж X5 на эмуляторе держит заглушку до ~2 мин, плановые оседали
  на ней и выдавали честный, но бесполезный PageFailure.
- *Прикрепление читалки.* План («как в зонде») предполагал не прикреплённую
  панель; на Android у отсоединённого WebView JS не выполняется
  (`evaluateJavascript` отдаёт null → IllegalStateException в прогреве), а
  WAF-челлендж отвергает вьюпорт 1×1/вынесенный за экран. WebView прикрепляется
  к `android.R.id.content` на MATCH_PARENT с alpha 0.02 — не виден, но живёт в
  иерархии окна, как требует движок; после ответа снимается и destroy().
  Вставка ПОВЕРХ (последним ребёнком) принципиальна: в конфиге «читалка ПОД
  интерфейсом» (первым ребёнком) челлендж не доходил до конца на живом
  прогоне — без кадров отрисовки rAF-челлендж замирает. Касания при этом
  от неё не уйдут ни к странице, ни мимо приложения: clickable/enabled
  выключены, жесты падают сквозь в WebView интерфейса — clickjacking и
  «зависание» экрана на время чтения исключены.
- *Страховка очереди:* колбэк `evaluateJavascript` мог вообще не прийти
  (смерть рендерера WebView) — поллер не оседал бы никогда, опрос замолкал до
  перезапуска. Теперь per-job страховка: гарантированный reject + jobDone
  поздним выстрелом, поздние колбэки проходят мимо (guard по view и
  «оседание — ровно один раз»). Гэп 2 с между открытиями считается и на
  опустевшей очереди (раньше обходился при быстрых чтениях подряд), редкие
  исключения моста не срывают полл до бюджета, host-allowlist хранится и на
  Java-стороне requireUrl, readCookies — только отладочная сборка, HTML-начало
  ответа поиска классифицируется как PageFailure (челлендж без текстовых
  маркеров обязан ретраиться, а не маскироваться под дрейф формы).
- *CSP `android.html`:* `connect-src 'self'` и `script-src 'wasm-unsafe-eval'` —
  иначе WebView запрещает sql.js fetch СВОЕГО ассета (`sql-wasm.wasm`, HTTP 200,
  application/wasm, 658410 Б) и компиляцию wasm, база не открывается.
  Renderer от чужих адресов по-прежнему не фетчит: сеть адаптеров — нативный
  слой (CapacitorHttp + page-reader), в APK скрипты отладки не уезжают.
- *Регистрация плагина ДО `super.onCreate`* (порядок шаблона Capacitor):
  после — плагин не попадает в реестр моста, probe молчит и Пятёрочка не
  регистрируется в сборке.
- *BODY_JS/READY_JS возвращают объект, не `JSON.stringify`*:
  `evaluateJavascript` сам JSON-кодирует результат, строка приезжала в Java
  дважды закодированной и ломала `parseJsValue`.
- *Oседание pollBody:* complete && len > 0 && !wafStub — иначе первый опрос
  успевает исполниться на about:blank до навигации и мгновенно оседает
  пустым; WAF-заглушка тоже не ответ, полл ждёт смены до бюджета.
- *Диагностика:* плагин получил `readCookies(url)` (CookieManager, только
  отладочная сборка) и wafStub-детект маркеров заглушки («Проблемы со
  связью», «request id», «проверьте настройки интернета и VPN») в
  pollWarmup/pollBody; неожиданный факт: CookieManager после успешного
  челленджа показывает `none` для 5ka.ru — антибот держит сессию в контексте
  открытых страниц, а не в видимой куке, повторный заход быстрый; это
  пересмотр п.5 плана («куки остаются в CookieManager»).
- *ToS-правила не тронуты:* штатный UA без подмены, пауза 2 с
  между открытиями, ≤2 попытки на адрес — как в плане и пре-ревью.

## Фаза 7г — Чижик и Перекрёсток на Android через ту же «страницу-читалку» (план, код после пре-ревью)

**База — измеренные факты десктопных транспортов, не догадки:**

- *Чижик* (`chizhik-browser.ts`, живой зонд 2026-10-08): обычный fetch к
  `app.chizhik.club/delivery/api/…` — 403; из контекста страницы — 200.
  Десктоп держит сессию на странице магазина `https://app.chizhik.club/shop/{sapId}`
  (goto + проверка пути) и делает in-page GET. `mode` обязателен (иначе 422),
  поиск принимает `q`. **`sap_code` в теле каталога НЕТ** — сверка точки только
  по URL: sapId подставляем сами из справочника, плюс сверка с городом
  (`storeFor` → StaleStoreError при расхождении). Строгий поиск по
  `query_type: "strict"`; не-strict с товарами — громкий отказ (НЕ
  ProductLookupError, иначе breaker отключил бы живую сеть). Пагинации полки нет
  (offset=200 → 404) — но полки вне v1 этой фазы.
- *Перекрёсток* (`perekrestok-browser.ts`, живой зонд 2026-10-10): POST
  `https://www.perekrestok.ru/api/customer/1.4.1.0/catalog/product/feed` — 200
  из контекста страницы `https://www.perekrestok.ru/catalog/`; native fetch —
  401 ДАЖЕ с правильным токеном и заголовками. Токен — кука `session` (JSON,
  поле `accessToken` → заголовок `auth: Bearer`); deviceId — localStorage
  `_SPUID` (заголовок `x-device-id`); сайт ставит их асинхронно (десктоп поллит
  30×1с). Заголовки ТОЛЬКО `content-type`/`accept`/`auth`/`x-device-id` —
  лишние не подтверждены и могут менять выдачу. Тело ровно
  `{page: 1, perPage: 100, filter: {textQuery}}` (perPage 500 → 400 — потолок
  сети). Точка опознаётся по `content.sapId` (единственная сверка в теле),
  strict — по `content.searchType`. GAP 2с, 2 попытки сессии, backoff 5с.

**Что берём из 7в без изменений:** весь каркас `PageReaderPlugin` (watchdog
страховка очереди, per-job settled-флаг, гэп 2с и на опустевшей очереди,
host-allowlist на Java-стороне, штатный UA, бюджетные поллы), прикрепление
ПОВЕРХ интерфейса (последним ребёнком, alpha 0.02, clickable/enabled off),
регистрация адаптеров по живому probe моста, форма юнит-цикла
`scripts/test-5ka-page.ts`, гейты.

**Три отличия от 7в, и каждое по измеренной причине:**

1. **Чижик может обойтись БЕЗ нового кода плагина — решает зонд.** Прямая
   навигация на API-URL — это ровно приём 5ka (`readPage`): открытая страница
   и есть JSON, WebView сам проходит челлендж. Десктопный Чижик прямой
   навигацией НЕ проверялся (там сразу in-page GET), поэтому зонд ПЕРЕД кодом
   адаптера, на том же URL, что поедет в транспорт (limit=48 — PAGE Чижика,
   не 12): `…/v3/stores/{sap}/search?mode=delivery&include_restrict=true&limit=48&q=молоко`.
   Критерий успеха (пре-ревью P1): тело JSON И содержит массив `products` —
   ошибочный JSON (`{"detail": …}`) тоже JSON, успехом не считается. Лестница
   зонда = рантайм-лестница транспорта: а) readPage на API-адрес; б) отказ —
   тело отказа сохраняется ЦЕЛИКОМ (readPage статуса не отдаёт; без снимка
   «PageFailure/челлендж vs дрейф» не классифицируется), повторные пробы — с
   паузами, не долбить; в) заглушка/403 → warmup страницы магазина
   `https://app.chizhik.club/shop/{sapId}` → повторный readPage (вторая из
   ≤2 попыток на адрес); г) если и так не отдаёт — in-page GET в каркасе
   POST-метода (пустое тело), включается по итогу зонда. Итог зонда
   фиксируется в этом разделе, потом код. Сверка Чижика остаётся ТОЛЬКО по
   URL: маркера магазина в теле нет, поэтому `storeFor` (справочник + город)
   обязателен в каждом вызове; при варианте г результат GET возвращает
   финальный `location.href` — сверка pathname `/shop/{sapId}`, как десктоп.
2. **Перекрёстку нужен POST из контекста страницы** — прямой
   fetch/CapacitorHttp не годится (401 даже с токеном, измерено). ПРЕ-РЕВЬЮ
   P0: план опирался на непроверенный факт — десктоп читал токен через
   `context.cookies()` Playwright, а `document.cookie` HttpOnly НЕ видит;
   если сеть ставит `session` HttpOnly, полл кредов мёртв по построению.
   Зонд кредов ДО кода (та же пересборка, что у Чижика): а) readPage на
   `https://www.perekrestok.ru/catalog/` — оседает ли документ без челленджа;
   б) `readCookies('https://www.perekrestok.ru')` — есть ли кука `session` в
   jar и парсится ли (decodeURIComponent → JSON → `accessToken`); в)
   `document.cookie` открытой страницы — видит ли JS ту же куку; г) `_SPUID`
   в localStorage — пробно через временную DevTools-цель открытой страницы,
   если target успевает, иначе факт снимет первый пост-метод (in-page JS
   скажет наличие сам). Фолбэк INSIDE метода: `document.cookie` молчит →
   Java-полл через `CookieManager.getCookie(url)` (jar видит HttpOnly),
   значение инжектится в in-page JS константой через JSON.stringify, в логи
   не печатается.
   Сам метод — `post({pageUrl, apiUrl, bodyJson})` → `{status, body}` поверх
   каркаса 7в: прикрепление ПОВЕРХ → load pageUrl → полл документа DOM (2с,
   оседание: complete && len > 0 && !wafStub) → один in-page JS, который сам
   читает креды (`session`→`accessToken`, `_SPUID`), стреляет подписанный
   fetch POST (четыре подтверждённых заголовка `content-type`/`accept`/
   `auth`/`x-device-id`, `credentials: 'include'`, AbortController ≤30с) и
   кладёт `{status, body}` в window-флаг — Java поллит флаг 1–2с до бюджета
   и оседает объектом; токен не покидает страницу (обе половины ловушки 7в —
   двойное JSON-экранирование и подстановка в JS-литерал без stringify —
   названы и закрыты). Механизм обязателен по пре-ревью P1: на этом WebView
   `evaluateJavascript` не дожидается Promise — асинхронный результат
   забирается ТОЛЬКО флагом и Java-поллом. Бюджеты (чтобы сторожка
   WATCHDOG_MS=165с не убила живой запрос): page-полл 90с + креды 30×1с +
   fetch ≤30с = 165с на пределе; при движении констант сторожка
   пересчитывается. Java-сторона проверяет ОБЕ URL до запуска (пре-ревью P1,
   renderer дозванивается до плага напрямую): каждая в host-allowlist И
   `apiUrl` same-origin с `pageUrl`, иначе разрешённый pageUrl стал бы
   трамплином fetch на чужой адрес. HTTP ≠ 200 — транспортная ошибка С ТЕЛОМ
   ответа, не молчаливая пустота (401/429/блок — причина в теле). ≤2 попытки
   на адрес, повтор — по расписанию через PageFailure. Сессию между вызовами
   НЕ держим (читалка 7в живёт ровно на вызов); полный цикл (загрузка
   каталога + POST) замеряется зондом ДО включения сети в scheduler — пре-
   ревью P1: если дороже ~8–10с, страница-донор обязательна прежде
   регулярного опроса (fetchProduct = лестница 40/25 → 1–3 загрузки, иначе
   N товаров × 3 загрузки каталога за проход).
3. **У обеих сетей нет `__NEXT_DATA__`** — `readNextData` не участвует;
   `fetchProduct` у Чижика — поиск по plu из ключа (лестница имени
   `chizhikNameQueries`), у Перекрёстка — поиск по имени (лестница 40/25):
   карточек по коду у обоих НЕТ (404, измерено на десктопе).

**Транспорт `src/core/adapters/chizhik-page.ts`** (после итога зонда):
`StoreAdapter` поверх page-reader, v1 — ТОЛЬКО `search` + `fetchProduct`
(полки/категории вне v1, как у `5ka-page.ts`: в телефоне не рисуются).
`PAGE=48`, строгий поиск `assertStrictQuery` переносится из `chizhik.ts` как
есть (обязательная метка при непустой выдаче; та же ловушка Магнита),
`storeFor` — обязателен (маркера в теле нет), нормализация через
`chizhik-parse.ts` без изменений. Классификация страниц (пре-ревью P1 — у
Чижика свои маркеры, X5-набор wafStub не годится): свой deny-набор из
десктопного `assertBlockPage` («доступ ограничен», «доступ запрещён»,
blocked/forbidden/antibot) и правило «тело начинается с `<` → PageFailure
(повторяемый отказ)»; JSON-тело отказа Чижика не имеет права
классифицироваться как «смена ответа сети» — дрейф даёт strike ВСЕЙ сети, а
отказ антибота не дрейф. «Strict + пустая выдача» — честная пустота, НЕ отказ
деградации (desktop-семантика Чижика; правило 5ka-page «пустой ответ поиска →
отказ» слепо не копировать). Хелперы (`assertStrictQuery`, `storeFor`)
переносятся экспортом из десктопных модулей, не клонами: клон разойдётся при
первой же правке десктопа.

**Транспорт `src/core/adapters/perekrestok-page.ts`:** `search` +
`fetchProduct`; тело запроса и PAGE=100 — ровно как у десктопа (лишний
