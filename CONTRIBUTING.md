# Как contribute

Спасибо, что хотите помочь. Ниже — короткая памятка: что нужно, чтобы собрать
проект, что обязательно проверять перед PR и каких правил проекта ждут от
изменений.

Проект — настольный агрегатор цен Пятёрки, Магнита и Ленты под Windows. Он
локальный: цены, история и избранное лежат в `prices.db` на вашем диске и никуда
не отправляются. Адаптеры сетей неофициальные и сделаны для личного пользования —
это важно, потому что от этого зависят и правила, и допустимые изменения.

## Что нужно

- **Node 22** (`node -v` должен показать v22.x) и npm.
- **Windows** для сборки установщика: `electron-builder --win nsis portable`.
  На других системах можно править код и гонять тесты, но `.exe` не соберётся.
- Никаких нативных модулей: база — `sql.js` (WASM), пересборка `node_modules`
  не нужна.

```bash
npm install
```

## Проверки перед PR

Первые три команды обязательны всегда, четвёртая — если затронут интерфейс.
Это не формальность: проект уже терял ~600 строк исходника одним неудачным
`regex` и восстанавливал их по собранному бандлу.

```bash
npx tsc --noEmit                              # renderer + shared
npx tsc -p tsconfig.electron.json --noEmit    # main + preload
npm test                                      # юнит-цикл на фикстурах
npx vite build                                # если трогали интерфейс
```

Покрытие и его порог:

```bash
npm run test:coverage         # отчёт: строки / ветки / функции
npm run test:coverage:check   # тот же замер с гейтом 100 / 100 / 100
                             # (строки / ветки / функции) — валит откат
```

Гейт применяется ко всему `src/**`, кроме `src/renderer` (его проверяет
браузерная регрессия на Playwright) и `electron/` (main и preload под Node не
исполняются). Новая логика в ядре идёт вместе с тестом — иначе гейт не
пройдёт. Браузерный транспорт адаптеров тоже покрыт: через порт
`src/core/adapters/playwright-port.ts` он запускается на фейке браузера.

Полная сборка (нужна для релиза, обычному PR не требуется):

```bash
npm run build
```

Порядок важен: `vite build` вытирает `dist/` целиком, поэтому голый `vite build`
после упаковщика удалит `.exe`.

## Как устроен код

| Путь | Что внутри |
|---|---|
| `electron/` | main и preload оболочки; preload собирается строго в CJS |
| `src/core/adapters/` | неофициальные адаптеры Пятёрки, Магнита, Ленты |
| `src/core/db/` | SQLite (`sql.js`): `schema.sql`, `db.ts` |
| `src/core/services.ts` | ядро целиком — тот слой, что виден из IPC |
| `src/renderer/` | React-интерфейс |
| `src/shared/` | контракты и правила: `types.ts`, `api.ts`, `catalog.ts`, `taxonomy.ts`, `matching.ts`, `format.ts`, `lenta-regions.ts` |
| `scripts/` | тесты, живые пробы, генерация схемы и сида |
| `tests/fixtures/` | обезличенные ответы сетей, на них стоят юнит-тесты |

Три правила, которые ломают проект чаще всего:

1. **Цена всегда привязана к `(canonicalId, storeId, city)`.** Ключ цены не
   может стать «город вообще»: у Пятёрки это `sapCode`, у Магнита `shopCode`, у
   Ленты `storeId`. Новый город — новая строка в `stores`, коды не меняются.
2. **В `prices_history` пишем только при изменении** цены, промо или наличия
   (`savePriceIfChanged`). Опрос по расписанию обязателен — без запроса
   изменение не узнать, — но запись идёт по изменению.
3. **Никаких заглушек.** Реализованная функция обязана работать; на заглушку
   можно опереться только в заведомо недостижимой ветке.

## Правила для изменений сети

Адаптеры ходят на живые сайты, поэтому:

- прямой `fetch` — основной путь; при 401/403 допустим fallback на браузер
  (Playwright warmup), но **не молчаливый пропуск**: сеть без ответа должна быть
  видна в интерфейсе причиной;
- сверка ответа с нашим магазином обязательна, когда сеть это позволяет;
- уважайте rate-limit, не гоняйте циклы по сети в тестах;
- живые пробы — отдельные скрипты `scripts/probe-*.mjs` / `probe-*.ts`, в
  `npm test` они не входят;
- добавляя город, проверьте код магазина живым поиском и запишите результат в
  `ROADMAP.md`.

## Секреты и личные данные

- Ключи, куки и токены — только в `.env`, никогда в код, логи и коммиты.
- `*.har` не коммитится: в дампах живые токены сессии (`Passport-*`, `qrator_*`).
- Фикстуры в `tests/fixtures/` — обезличенные. Выкладывать в репозиторий
  ответы с заголовками авторизации нельзя.

## Ревью

Изменения в адаптерах, БД и интерфейсе проходят ревью: отдельно смотрят логику
и нормализацию цен, работу с сетью и коды магазинов, интерфейс, секреты и SQL.
Замечания, которые верны, исправляются сразу; спорные выносятся на обсуждение с
аргументами обеих сторон.

По `ROADMAP.md`: отмечайте пункт `[x]` только после того, как он реально
работает, и правьте формулировки, которые описывают поведение изменившейся части.
Числа в документе должны совпадать с измерениями — если пишете про покрытие,
приложите команду, которой оно меряется.

## Коммит и PR

- Коммиты не делаются без явной просьбы: сначала согласуйте изменения.
- Сообщение коммита — коротко и по существу, в стиле репозитория.
- В PR опишите, что изменилось, чем это проверено и что осталось непроверенным.
  Если что-то проверено только живой пробой — скажите прямо.
- Крупные фичи (новый адаптер, планировщик, алерты) начинаются не с кода, а с
  плана, который проходит ревью до реализации.
